# MEDIC — Медицинская Информационная Система (МИС / EMR)

Комплексная система автоматизации процессов для сети медицинских клиник с многоролевым доступом, электронной медицинской картой (ЭМК), расписанием приёмов, учётом выполнения процедур и финансовой отчётностью для бухгалтерии.

---

## 🛠 Технологический стек

* **Бэкенд:** Python 3.12, FastAPI, Pydantic v2
* **База данных:** PostgreSQL 16, SQLAlchemy 2.0 (asyncio + asyncpg), Alembic
* **Кэш и брокер:** Redis 7, RabbitMQ 3.13, Celery, Flower
* **Обработка файлов:** Pillow (оптимизация сканов, создание превью)
* **Качество кода:** uv, Ruff, standard `unittest`
* **Инфраструктура:** Docker, Docker Compose, Nginx, GitHub Actions, Loguru

## 👥 Ролевая модель доступа (RBAC)

У пользователя может быть **несколько ролей одновременно** (`user.roles`):
в небольшой клинике один человек бывает и врачом, и главврачом, и админом
с ресепшеном. Права при этом суммируются.

| Роль | Ключевые возможности |
|---|---|
| **Супер-админ** (`super_admin`) | Владелец платформы. Управляет клиниками, сотрудниками и тарифами всей сети (🌐). Не подчиняется главврачу. Защищён от самоудаления и удаления другого администратора, не может менять/удалять финансовые проводки |
| **Админ клиники** (`clinic_admin`) | Административный директор филиала (🏥). Люди, графики, доступы, кассовые операции. **НЕ читает ЭМК** и не создаёт назначения — это зона главврача |
| **Главный врач** (`head_doctor`) | Медицинское качество (🌐 по медданным): ЭМК, назначения, контроль, финотчёты. **Не управляет сотрудниками** — это зона админа клиники |
| **Врач** (`doctor`) | Ведёт приёмы (Encounter), создаёт назначения, вносит записи в ЭМК. Видит карты только тех пациентов, с которыми есть связь (приём) — правило «по касанию» |
| **Медсестра** (`nurse`) | Просматривает карточку, назначения и анализы, вносит отметки о выполнении процедур и о прибытии пациента. **Не читает врачебные записи ЭМК** (осмотры, диагнозы, МКБ-10) |
| **Ресепшен** (`receptionist`) | Создаёт карты пациентов по паспорту, ведёт расписание, принимает оплату, выдаёт доступ в ЛК. Карточка — без ЭМК |
| **Бухгалтерия** (`accountant`) | Единая бухгалтерия сети (🌐). Финансовые отчёты, зарплаты, возвраты. **Не имеет доступа к медданным и ПДн** |
| **Пациент** (`patient`) | Видит только своё — карту, приёмы, назначения, анализы, счёт. Записывает себя и близких, переносит/отменяет свой приём за 24 ч, правит свои контакты |

### Ключевые правила доступа

* **Изоляция по клинике (🏥):** большинство операций — только в рамках своего филиала. Сеть (🌐) — у SA, главврача (медданные) и бухгалтерии (финансы).
* **«По касанию»:** врач видит ЭМК, сканы и назначения только пациентов, с которыми есть связь через Encounter (приём).
* **Разделение ролей:** медсестра выполняет процедуры, но не читает ЭМК; админ клиники управляет людьми, но не читает ЭМК; главврач отвечает за медицину, но не управляет сотрудниками.
* **Двойной контроль финансов:** возвраты и сторно — только через заявку (касса) и подтверждение (бухгалтерия). Свою заявку подтвердить нельзя.
* **Логирование ПДн (152-ФЗ):** каждое открытие ЭМК/скана паспорта пишется в `audit_logs` как `VIEW_PDN`.

## 🏗 Архитектура и слои

Проект построен по слоистой схеме — каждый слой знает только о нижележащем:

```
HTTP-запрос
   │
   ▼
[ api/v1/*.py ]      Роутеры: валидация DTO, ролевой guard (require_roles), вызов сервиса
   │
   ▼
[ services/*.py ]    Бизнес-логика: правила, инварианты, объектные проверки доступа
   │
   ▼
[ repositories/*.py ] Доступ к данным: SQL-запросы, CRUD
   │
   ▼
[ models/entities.py ] SQLAlchemy-модели (таблицы БД)
```

**Сквозные модули:**
* `core/access.py` — вся логика разграничения доступа (см. ниже).
* `core/logging.py` — логирование с контекстом запроса и пользователя.
* `api/deps.py` — FastAPI-зависимости; ре-экспортирует права из `core/access.py`.

### Двойная проверка доступа

Каждый защищённый эндпоинт проходит **два уровня** проверки:

1. **Ролевой (в роутере)** — `require_roles(...)` / `require_super_admin()`:
   *«может ли эта роль в принципе делать такую операцию?»*
2. **Объектный (в сервисе/роутере)** — `ensure_medical_access`, `ensure_patient_card_access`,
   `ensure_clinic_scope` и т.п.: *«есть ли у этого пользователя право на этот объект?»*

Пример эталонного эндпоинта:

```python
current_user: Annotated[User, Depends(require_roles(*EMR_READ_ROLES))]  # уровень 1
...
await ensure_medical_access(db, current_user, patient_id)  # уровень 2
```

## 🔐 Модуль доступа `app/core/access.py`

Единая точка правды для разграничения доступа. Не зависит от FastAPI —
вызывается и из роутеров, и из сервисов. Содержит 5 групп:

| Группа | Что это | Примеры |
|---|---|---|
| **1. Константы ролей** | Именованные наборы ролей | `EMR_READ_ROLES`, `FINANCE_ROLES`, `NETWORK_MEDICAL_ROLES` |
| **2. Предикаты** | Быстрые проверки роли | `is_admin()`, `is_medical_staff()`, `can_view_emr()` |
| **3. Кирпичики** | Атомарные объектные проверки | `ensure_patient_self()`, `ensure_clinic_scope()`, `ensure_doctor_touch()` |
| **4. Guard-функции** | Составные проверки из кирпичиков | `ensure_medical_access()`, `ensure_patient_card_access()`, `ensure_analysis_access()`, `ensure_patient_admin_access()`, `ensure_doctor_clinic_access()` |
| **5. Резолверы** | Достают `patient_id` из связанных сущностей | `resolve_patient_id_from_record()`, `resolve_patient_id_from_assignment()` |

**Ключевые константы:**
* `NETWORK_MEDICAL_ROLES` = {SA, главврач} — сквозной доступ к медданным сети (🌐).
* `NETWORK_FINANCE_ROLES` = {SA, бухгалтерия} — сквозной доступ к финансам сети (🌐).
* `PASSPORT_SCAN_VIEW_ROLES` = `PASSPORT_SCAN_ROLES` − {ресепшен} — ресепшен скан только грузит, но не читает.

## 🗃 Тонкости модели данных

* **`Patient` НЕ имеет `clinic_id` как «принадлежности».** Карта пациента —
  общая для всей сети (по ТЗ: «карта общая, доступ по касанию, а не по
  членству в клинике»). Пациент может лечиться в нескольких филиалах
  одновременно — это норма, а не аномалия. Принадлежность клинике
  определяется **фактами взаимодействия**, а не меткой на карте.
* **`Patient.created_by_clinic_id`** — клиника, чей сотрудник завёл карту.
  Это **факт регистрации**, а не «владение». Используется только для
  административных операций над картой, у которой ещё нет приёмов.
* **`Appointment` ≠ `Encounter`** (стандарт FHIR):
  * `Appointment` — бронь времени (слот). Создаёт ресепшен/пациент/врач.
  * `Encounter` — медицинское событие (осмотр, МКБ-10). Создаёт врач.
  * Один `Appointment` порождает ноль или один `Encounter`.
* **`User.roles` — список ролей** (`list[str]`), а не одна роль. Права суммируются.
  Свойство `user.role` (первая роль) оставлено только для обратной совместимости.
* **Ничего не удаляется физически** — только статусы (архив, отмена, сторно).
  Оригиналы финансовых проводок сохраняются всегда.
* **`DoctorSchedule` и `TimeOff` имеют `clinic_id`** — изоляция по клинике здесь однозначна.

## 🔒 Правило доступа к карте пациента (зафиксировано)

**Приём — источник истины.** Доступ к данным и операциям над картой
определяется реальными взаимодействиями, а не меткой «принадлежности»:

| Тип доступа | Правило |
|---|---|
| **ЭМК, назначения, анализы, сканы** | Строго «по касанию»: есть `Encounter`/`Appointment` с пациентом. Без исключений |
| **Админ-операции над картой** (выдача ЛК, активация, архивация, обезличивание, правка реквизитов) | Приём в своей клинике **ИЛИ** `created_by_clinic_id == user.clinic_id` для карт без приёмов |
| **Списки пациентов для персонала** | Через подзапрос по `appointments.clinic_id` |
| **SA и главврач** | По всей сети (🌐), как и раньше |

Реализовано в `ensure_patient_admin_access()` (`app/core/access.py`).

**Почему так, а не `clinic_id` на карте:**
* Пациент не «записан» в клинику — он в неё *обращался*. Поле `clinic_id`
  кодировало бы ложное «этот пациент принадлежит только нам».
* Контрпример: пациент зарегистрирован в филиале А, переехал и лечится в Б.
  С `clinic_id` на карте врач из Б не увидел бы приёмы без спецлогики-обхода.
  С проверкой через приёмы всё работает само: есть приём в Б — есть доступ в Б.
* Единственная непроверяемая операция — карта **без приёмов** (новый черновик).
  Её закрывает `created_by_clinic_id`: карту до первого приёма правит только
  та клиника, чей сотрудник её создал.

## ⚠️ Известные ограничения и точки внимания

* **`GET /users/doctors`** ограничен клиникой сотрудника (кроме SA/главврача).
* **`GET /appointments`** недоступен бухгалтерии; персонал видит только свой филиал.
* **Просмотр скана паспорта** запрещён ресепшену (только загрузка).
* **Расписание врача** (`/schedules/*`) — управление и просмотр только для
  персонала своей клиники (кроме SA); пациент видит лишь свободные слоты.
* **Загрузка анализа** (`/analyses/upload`) — только по назначению, выданному
  в клинике сотрудника.

## 🔒 Безопасность конфигурации (production)

При `APP_ENV=production` приложение **не стартует** с небезопасной конфигурацией —
срабатывает валидатор `Settings._validate_production_secrets`:

| Проверка | Условие отказа |
|---|---|
| `SECRET_KEY` | значение по умолчанию или короче 32 байт (RFC 7518 для HS256) |
| `BOOTSTRAP_ADMIN_PASSWORD` | дефолтный `Admin12345` при `BOOTSTRAP_ADMIN_ON_STARTUP=true` |
| `DEBUG` | `true` (утечка деталей ошибок) |

Сгенерировать надёжный ключ:

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

В `development`/`test` дефолты допустимы — для удобства локального запуска.
